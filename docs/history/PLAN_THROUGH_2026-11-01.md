read answers and sources in ChatGPT**. The default UI no longer retrieves quotes
or displays model answers itself. It uses the existing ChatGPT account, without
new provider signup, a paid search/model API, automatic submission, scraping,
session reuse, or importing ChatGPT answers. Opening the plain ChatGPT URL does
not transmit the prepared question; copying is a separate explicit action.

**Why:** real-time data API access introduced provider display/AI-use licensing
questions, extra account/personal-information exposure, cost uncertainty and
integration work disproportionate to this personal learning tool. Web research
is sufficient for the user's immediate need; it is not guaranteed real-time
exchange data and is not guaranteed to search Google exclusively. Search should
request sources, quote time/timezone/currency/session, uncertainty and an honest
unavailable result. Search access remains subject to the user's ChatGPT limits.

## 4. Key Design Decisions

### 4.1 Asynchronous API

Starting a Fargate task and waiting for it to retrieve data or call Bedrock can exceed a comfortable HTTP request duration. Both user actions therefore create jobs:

1. Client submits a request.
2. API returns `202 Accepted` with a `jobId`.
3. Client polls the job endpoint with bounded exponential backoff.
4. Worker stores the result.
5. Client renders the completed result or a terminal error.

The UI should say `Starting secure worker…` rather than pretending the action is instantaneous. Cold-start latency is an intentional tradeoff of the cost-saving architecture.

### 4.2 One worker image, two operation modes

The same container image supports `PRICE` and `ANALYZE` operations. The job record identifies the operation. This reduces duplicate deployment artifacts while keeping the code paths separable and testable.

### 4.3 Market data stays server-side

The browser never receives the market-data API key. The Fargate task reads it at runtime from AWS Systems Manager Parameter Store `SecureString` or AWS Secrets Manager.

- Prefer **Parameter Store SecureString** for the first low-cost version if rotation is not required.
- Prefer **Secrets Manager** if automatic rotation, richer auditing, or future multi-secret management justifies the additional cost.

### 4.4 Honest price semantics

The UI must label data based on provider metadata:

- `Real-time` only when the provider contract explicitly guarantees it.
- `Delayed` when delayed.
- `Latest available` or `Previous close` outside market hours when appropriate.

Every displayed quote includes currency, market timestamp, retrieval timestamp, market status, and source/provider label.

### 4.5 Bedrock is grounded in supplied facts

The model receives a compact JSON facts block produced by the worker. It is instructed to use only supplied facts, state uncertainty, avoid personalized recommendations, and return a validated structured response. A disclaimer is added by application code, not entrusted only to the model.

## 6. Non-Functional Requirements

### Reliability

- All jobs have terminal states and expiration times.
- Worker processing is idempotent by `jobId`.
- Conditional DynamoDB updates prevent completed results from being overwritten.
- Fargate task stop timeout and application timeout prevent runaway processing.
- Job sweeper marks abandoned queued/running jobs as `TIMED_OUT`.

### Performance

- API job creation target: p95 under 2 seconds, excluding provider or AWS control-plane incidents.
- Job status lookup target: p95 under 500 ms.
- Price job completion target for portfolio demonstration: commonly under 60 seconds after warm AWS control-plane conditions, but not a hard SLA.
- Analysis target: commonly under 90 seconds, dependent on task launch and model latency.

### Security

- TLS only at CloudFront and API Gateway.
- No secrets in source control, image layers, frontend bundles, task overrides, or logs.
- Least-privilege roles are separate for Lambda, ECS task execution, and ECS worker runtime.
- CloudFront uses Origin Access Control so the S3 bucket is not public.
- All inputs are allowlisted and schema-validated.

### Maintainability

- Infrastructure is defined in AWS CDK, Terraform, or CloudFormation; choose one and use it consistently.
- Business logic is isolated from AWS adapters and external provider adapters.
- Locale resources are independent from components.
- Environment-specific names and IDs are configuration, not hard-coded.

### Accessibility and usability

- Keyboard-accessible buttons and language selector.
- Visible focus indicators, semantic headings, sufficient color contrast, and live-region updates for job status.
- Dates and numbers use locale-aware formatting while preserving the exchange timezone.

## 8. Request Flows

### 8.1 Check Price flow

1. User chooses a symbol and locale and presses **Check Price**.
2. Frontend sends `POST /v1/jobs` with `operation=PRICE` and an idempotency key.
3. API Gateway invokes the controller Lambda.
4. Lambda validates the schema, symbol allowlist, locale, rate limits, and circuit state.
5. Lambda conditionally writes a `QUEUED` job to DynamoDB.
6. Lambda calls `ecs:RunTask` with a fixed cluster, task definition, subnets, and security group. Only `JOB_ID` is provided as an override; no secret is passed.
7. Lambda records the ECS task ARN when launch succeeds and returns `202`.
8. Worker reads the job, conditionally changes it to `RUNNING`, and retrieves the provider credential.
9. Worker calls the market-data provider with timeouts and bounded retries.
10. Worker normalizes the response, validates timestamp/symbol/currency, and writes a `SUCCEEDED` result.
11. Frontend polls `GET /v1/jobs/{jobId}` and renders the result.
12. On failure, worker writes a stable public error code and a sanitized message; detailed diagnostics remain in logs.

### 8.2 Analyze flow

1. User presses **Analyze**.
2. Frontend creates an `ANALYZE` job through the same endpoint.
3. Lambda validates, stores, launches, and returns the job ID as above.
4. Worker retrieves current market data and constructs a normalized fact package.
5. Worker builds a versioned prompt containing locale, asset metadata, facts, constraints, and required JSON schema.
6. Worker invokes an approved Bedrock model with conservative generation settings and an output-token cap.
7. Worker parses and validates the model response. One constrained repair attempt may be made for invalid JSON; otherwise the job fails safely.
8. Application code attaches the canonical localized disclaimer and provenance metadata.
9. Worker stores the structured result in DynamoDB and emits duration/token/error metrics.
10. Frontend retrieves and renders analysis sections in the selected language.

### 8.3 Failure and timeout flow

- If `RunTask` fails, Lambda conditionally changes the job to `FAILED` with `TASK_LAUNCH_FAILED`.
- If the provider rate-limits requests, the worker respects `Retry-After` when present and performs limited jittered retries.
- If Bedrock throttles or times out, the job terminates with a retryable public error code; the UI may allow one deliberate retry.
- An EventBridge-scheduled sweeper finds jobs past `deadlineAt`, describes/stops the related task if necessary, and marks them `TIMED_OUT`.
- Alarm thresholds may open the circuit to stop new task launches and notify SNS subscribers.

## 10. DynamoDB Data Model

Use one table, for example `global-market-ai-jobs-<environment>`.

### Primary key

- Partition key: `jobId` (string)

For the expected portfolio traffic, a single-item-per-job design is sufficient. Add a GSI only when an access pattern requires it.

### Job attributes

| Attribute | Purpose |
|---|---|
| `jobId` | ULID/UUID public identifier |
| `operation` | `PRICE` or `ANALYZE` |
| `symbol` | Validated allowlisted ticker |
| `locale` | `en`, `ja`, or `ko` |
| `status` | `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `TIMED_OUT` |
| `idempotencyKeyHash` | Hash of client key; never rely on raw key as authorization |
| `requestHash` | Detects conflicting idempotent retries |
| `createdAt`, `updatedAt` | ISO 8601 audit timestamps |
| `deadlineAt` | Processing deadline used by worker/sweeper |
| `expiresAt` | DynamoDB TTL epoch value |
| `taskArn` | Internal correlation for operations; omit from public API |
| `result` | Normalized price or analysis document |
| `errorCode` | Stable machine-readable failure code |
| `errorMessage` | Sanitized user-safe failure detail |
| `attemptCount` | Bounded attempt count |
| `version` | Optimistic concurrency/versioning |
| `schemaVersion` | Migration compatibility |

### State transitions

```text
QUEUED -> RUNNING -> SUCCEEDED
   |         |
   |         +----> FAILED
   +--------------> FAILED
   +--------------> TIMED_OUT
RUNNING ----------> TIMED_OUT
```

- Use conditional expressions for every state change.
- Terminal states are immutable except for explicitly versioned administrative repair.
- Keep raw provider payloads out of DynamoDB unless required for debugging; prefer normalized fields and short retention.
- Suggested development TTL: 1–7 days. Production-like demo TTL: 7–30 days, with the exact choice documented.

### Idempotency lookup

For a small project, add a GSI with `idempotencyKeyHash` as partition key or store a separate record using a namespaced key. Ensure TTL is applied and compare `requestHash` before returning an earlier job.

## 11. Worker Design

### Internal modules

- `job_repository`: DynamoDB reads and conditional state updates.
- `asset_catalog`: allowlisted metadata and special warnings.
- `market_data_provider`: provider interface and concrete adapter.
- `quote_normalizer`: validates symbol, currency, price, timestamps, and freshness.
- `analysis_service`: builds facts and invokes Bedrock.
- `prompt_templates`: versioned constraints and output schema.
- `result_validator`: validates all model/provider output before persistence.
- `telemetry`: structured logs, correlation IDs, and metrics.
- `config`: validated environment configuration and secret retrieval.

### Container contract

- Input environment: `JOB_ID`, `TABLE_NAME`, `SECRET_ID` or parameter name, region, model alias/ID, prompt version, and log level.
- Entrypoint validates configuration, loads only the indicated job, and exits non-zero on processing failure after persisting a terminal state where possible.
- Run as a non-root user on a read-only root filesystem where supported; use a small writable temporary directory only if needed.
- Pin dependencies and base image; generate an SBOM if practical.
- Set explicit CPU/memory and ephemeral storage after measurement, beginning with the smallest workable Fargate configuration.

### Market provider adapter

Evaluate providers during Phase 1 against:

- Coverage of all five symbols, especially `SPCX`.
- Quote freshness and licensing/display requirements.
- Free-tier request limit and overage behavior.
- Exchange timestamp, market-state, and currency fields.
- Historical data availability if future trend features are planned.
- Terms that allow server-side caching and portfolio demonstration.

Do not silently scrape a public website. Use an authorized API and comply with attribution and redistribution terms.

### Bedrock prompt/output contract

The prompt must:

1. Identify the system as an educational market explainer.
2. Include only normalized facts and timestamps.
3. Require the selected output language.
4. Forbid individualized buy/sell/hold instructions and guaranteed predictions.
5. Require uncertainty and data limitations.
6. Require valid JSON matching a versioned schema.
7. Instruct the model to omit a claimed driver when evidence is absent.
8. Explicitly highlight leveraged ETF mechanics for `QLD`.

The application validates output length, required keys, locale, and prohibited recommendation phrasing. Model output is untrusted data and must be escaped by the frontend.

## 12. IAM Roles and Permissions

### Controller Lambda execution role

Required actions should be resource-scoped where AWS supports it:

- CloudWatch Logs write permissions.
- `dynamodb:PutItem`, `GetItem`, `UpdateItem`, and required query operation on the jobs table/index.
- `ecs:RunTask` only for the approved task definition and cluster conditions.
- `ecs:DescribeTasks` and `ecs:StopTask` only if the controller owns those functions; otherwise assign them to the sweeper role.
- `iam:PassRole` only for the exact ECS execution and worker task role ARNs, ideally with `iam:PassedToService = ecs-tasks.amazonaws.com`.
- Read only the circuit-state parameter if Parameter Store is used.

Do not grant Lambda access to the market API secret or Bedrock if it does not call them.

### ECS task execution role

Used by the ECS agent, not application code:

- Pull image layers/authentication from the specific ECR repository.
- Write container logs to the specific CloudWatch log group.
- Retrieve injected secrets only if ECS secret injection is chosen. Prefer runtime retrieval by the task role when finer control and explicit handling are desired.

### ECS worker task role

- Read/update only items in the jobs table; use leading-key or other conditions when practical.
- Read only the exact Parameter Store parameter or Secrets Manager secret.
- `kms:Decrypt` only for the relevant customer-managed key if one is used.
- Invoke only the selected Bedrock model/inference profile and required guardrail resource.
- Emit custom metrics only to the chosen namespace if using direct metric calls.

The worker does not need `ecs:RunTask`, `iam:PassRole`, broad S3 access, or infrastructure-management permissions.

### Sweeper/circuit-control role

- Read/query stale jobs.
- Conditionally update stale jobs.
- Describe/stop only tasks in the project cluster.
- Update only the circuit-state parameter if automatic opening is enabled.
- Publish only to the operations SNS topic.

### Deployment role

- Used only in CI or by the developer to deploy infrastructure.
- Separate from runtime roles.
- Prefer short-lived OIDC federation in CI instead of long-lived access keys.
- Document permissions and bootstrap requirements.

### IAM verification

- Run IAM policy validation/access analysis where available.
- Confirm expected denies using policy simulation or negative integration tests.
- Record screenshots or sanitized policy excerpts for the portfolio README.

## 13. Security Design

### Data and secrets

- Encrypt S3, DynamoDB, ECR, log groups, parameters/secrets, and SNS using AWS-managed keys initially; document when a customer-managed KMS key is worth the cost/complexity.
- Never log API keys, authorization headers, raw prompts containing secrets, or full provider error bodies.
- Redact sensitive headers and query parameters in the HTTP client.
- Rotate the provider credential after any suspected exposure.

### Frontend and API

- Private S3 bucket with block-public-access and CloudFront Origin Access Control.
- HTTPS redirect and modern TLS policy.
- Security headers: CSP, HSTS, `X-Content-Type-Options`, frame restrictions, and a restrictive referrer policy.
- Escape all dynamic output. Do not render model text as raw HTML.
- Restrict CORS to deployed origins.
- Apply API Gateway throttling; optionally add WAF when the learning/cost value is justified.

### Container supply chain

- Use a pinned, minimal base image.
- Enable ECR scan-on-push or enhanced scanning if budget allows.
- Fail CI on critical known vulnerabilities according to a documented policy.
- Tag images with commit SHA; deploy by digest rather than mutable `latest`.
- Avoid package-manager caches and credentials in image layers.

### Abuse and prompt safety

- Users cannot submit free-form prompt text in v1.
- Symbol and locale are strict enums.
- Model input is constructed by server code from normalized provider data.
- Set model token limits and job-rate limits to prevent bill shock.
- Optional Bedrock Guardrails can be evaluated, but application-level validation remains mandatory.

### Auditability

- Correlate API request ID, `jobId`, ECS task ARN, provider attempt, and Bedrock invocation without exposing internals publicly.
- Retain only the logs needed for the demo and incident learning.
- Record architecture decisions and threat model in `docs/`.

## 15. Circuit Breaker and Guardrails

This project uses an **application/cost circuit breaker**, distinct from the later ECS deployment circuit breaker lab.

### Circuit states

- `CLOSED`: requests may create tasks.
- `OPEN`: new `PRICE` and `ANALYZE` jobs are rejected; status reads remain enabled.
- Optional `HALF_OPEN`: allow a small test request after a cooldown. Defer until the simpler design is reliable.

### Inputs that can open the circuit

- Provider rate-limit or authentication failures above threshold.
- Bedrock throttling or errors above threshold.
- ECS task-launch failures above threshold.
- Too many active/stale jobs.
- Manual operator switch.
- Cost signal or request-volume guard threshold.

### Implementation

1. Store state, reason, actor, update time, and expiry/cooldown in a dedicated Parameter Store parameter or DynamoDB control item.
2. Controller reads state before writing a new job or calling `RunTask`.
3. CloudWatch alarms publish to SNS for human visibility.
4. EventBridge rules or a small control Lambda may open the circuit for narrowly defined alarm events.
5. An EventBridge schedule runs the stale-job sweeper and guard evaluation.
6. Automatic closure should be conservative; prefer manual reset initially and record the change.

The circuit breaker is a defense in depth mechanism, not a guaranteed AWS billing cap. AWS Budgets and CloudWatch billing alarms may be delayed.

### Hard usage controls

- API Gateway route throttles and burst limits.
- Maximum jobs per time window in the controller, stored atomically.
- Fargate service quota awareness and cluster/task concurrency cap enforced by application counters.
- Provider-side spending/request caps when supported.
- Bedrock model and output-token caps.
- Short worker and job timeouts.

## 22. Risks and Tradeoffs

| Risk/tradeoff | Impact | Mitigation |
|---|---|---|
| Fargate task launch latency | Price checks feel slower than serverless functions or an always-on service | Async UX, clear progress, measure p95, later compare ECS service |
| External provider coverage for `SPCX` | Required ticker may be missing/ambiguous | Validate early; never substitute; show `DATA_UNAVAILABLE`; evaluate provider alternatives |
| “Real-time” licensing/freshness | Misleading user or violating terms | Display provider-defined freshness/source/timestamp; review terms |
| Free-tier/rate limits | Failed demos or unexpected charge | Server throttles, caching only when licensed, circuit breaker, provider caps |
| Public-subnet Fargate egress | Public IP increases perceived exposure | No inbound rules/listeners, short-lived tasks, patched image; document NAT tradeoff |
| Bedrock hallucination | Unsupported market explanations | Grounded facts, strict JSON schema, uncertainty, validation, disclaimer |
| AI content resembles advice | Regulatory/user-trust concern | No personalization or trade commands; explicit educational disclaimer and evaluations |
| DynamoDB polling | Extra requests and delayed display | Exponential backoff/jitter, terminal stop, later consider push mechanisms |
| One task per action | Inefficient at higher traffic | Appropriate for learning/low volume; later batching, queue, Lambda, or service comparison |
| Direct Lambda `RunTask` coupling | Launch failure needs compensation | Store job first, mark failure conditionally, metrics/alarms, idempotency |
| No queue in v1 | Limited buffering/backpressure | Concurrency guard/circuit; consider SQS + dispatcher later |
| Billing alerts are delayed | Spend can exceed USD 5 | Service quotas, request/token caps, short timeouts, manual circuit, regular cleanup |
| Multi-language quality varies | Inconsistent insight | Native-language fixtures/review, glossary, deterministic schema, fall back safely |
| Region/model availability | Deployment failure | Confirm region/model access early; use a logical model configuration |
